# 标注界面交互设计偏好

登记日期：2026-09-02。本文件记录标注界面（annotation UI）的**交互设计偏好**，供实现者（W5 D6-D7 交付物）遵循。偏好来源于主研究者；后续若有新增标注任务（W6 扰动合理性、E1 偏好标注），界面应复用此文档的约定。

## 0. 适用范围

当前服务 **E7（L3 parse accuracy 人工抽检，1 名标注者）**。后续 E1（300 对偏好标注）与 W6 D7（50 条扰动构造合理性）复用同一交互约定，但各自有独立的数据 schema 与判断字段。

**面向标注者的称呼（2026-09-07）**：统一使用「指令解析结果」，首次解释为「解析器把驾驶指令转换成的一组检查条件，列明对象、动作、时间关系和参数」。卡片称为「解析结果与上下文」，符号部分标为「形式化表达（AST）」，失败项显示「未生成指令解析结果」。技术字段 `program` 和 AST 数据结构保持原名；指令原文、人工备注和判断值不做文字替换。本次仅澄清术语，E7 口径版本和已提交状态不因此改变。

## 1. 核心偏好（强制）

1. **避免手工读 JSON**。标注者看到的应是**经过格式化的指令解析结果**（如 `eventually[0-7.9](stop(0.1))`），不是原始嵌套 JSON。实现者必须提供 AST 格式化器。
2. **标注操作以鼠标单击为主**。除「备注/自由文本」外，所有判断字段（Y/N/partial、Y/N/ambiguous、high/medium/low）都用**单次点击**完成，不键入。
3. **Agent 预生成 draft 标注决策，标注者只复查有异议处**。界面加载每条记录时，先由 agent（LLM 或规则）生成一个 `draft` 标注（含判断字段与简短理由），标注者看到的是「已填好的草稿 + 标记者可逐字段点击更改」。**避免标注者从零做每一条**——重复的判断由 agent 承担，人工只处理异议。
4. **逐条显示、单条提交**。每条记录一条卡片，标注者逐条处理；不允许批量粘贴、不允许修改形式化表达（AST）（那是解析器的输出，只读）。
5. **歧义合法**。若标注者对某字段不确定，选 `ambiguous` 或 `low confidence`，不强迫选边。

## 2. 标注界面布局建议

每条记录一张卡片，从上到下：

```
┌─────────────────────────────────────────────┐
│ ① 指令原文（instruction text，只读）              │
│   "Have <ego> decelerate and then come to a   │
│    complete stop."                           │
├─────────────────────────────────────────────┤
│ ② 指令解析结果（形式化表达，只读）               │
│   eventually[0-7.9](stop(0.1))               │
│   含：agent 绑定、窗口、谓词                    │
├─────────────────────────────────────────────┤
│ ③ Agent draft 标注（预生成）                    │
│   semantic_complete: partial (遗漏减速)      │
│   structure_correct: N (遗漏先后关系)         │
│   confidence: medium                        │
├─────────────────────────────────────────────┤
│ ④ 标注者复查区（可点击更改，初始等于 draft）        │
│   ○ Y  ● N  ○ partial                     │
│   ○ Y  ● N  ○ ambiguous                   │
│   备注（可选，手动输入）                         │
├─────────────────────────────────────────────┤
│ 提交（点击后下一张）                              │
└─────────────────────────────────────────────┘
```

- ② 中 AST 用 `eventually[0-7.9](stop(0.1))` 这种**线性文本**（比嵌套 JSON 易读），或者**树形展示**（缩进显示操作树）——二者由实现者选一种，但不得显示原始 JSON。
- ③ ④ 的关系：④ 初始 = ③；标注者**只对异议字段点击**，无异议直接 `提交`。
- 自由文本（备注、missing_capability）是唯一可键入的字段。

## 3. 数据流

```
data/w5/l3_parse_selection.json  +  200 条解析产物（parsed/failure 终态）
        ↓
scripts/build_annotations_draft.py   （agent 预生成 draft，工具脚本）
        ↓
data/w5/parse_accuracy_annotations.draft.json
        ↓
标注界面（W5 交付物）  ← 标注者操作
        ↓
data/w5/parse_accuracy_annotations.json  （最终标注结果）
```

- `build_annotations_draft.py` 是**离线工具**：读选择 + 解析产物，调 LLM 生成 draft 标注（含理由），输出 draft JSON。**draft 不是最终标注**，仅作界面初始值。
- 标注界面**不调用 LLM**（只读 draft + 用户点击），保证标注者操作时不被模型抖动干扰。
- 最终标注 JSON 的每条记录含：`scene_id` / `instruction_id` / 判断字段 / `draft_agreement`（标注者是否同意 draft）/ `annotator` / `date`。

## 4. draft 生成策略（预生成）

- **parsed 项**：draft 的 `semantic_complete` 与 `structure_correct` 由 LLM（复用 L3 解析器同一 provider，`deepseek-v4-flash`）根据「指令原文 + 形式化表达（AST）」生成，理由为模型对「指令解析结果是否覆盖指令」的判断。**注意**：draft 与解析器同源，可能系统性偏好解析器；标注者看到 draft 时必须能**容易地不同意**（即单击切换即可，不施加确认压力）。
- **failure 项**：draft 的 `rejection_correct` 由 LLM 根据「指令原文 + 缺失能力描述（来自模型 detail）」生成。**注意**：模型 detail 是失败原因码的**来源**（可能带偏），draft 生成时**不把模型 detail 直接显示给标注者**（标注者只见 draft 的简短理由，理由由 draft 生成器提炼，不含 `UNSUPPORTED_SEMANTICS` 等码）。
- **交互 20 条**：按真实终态分配字段，parsed 项同其他 parsed 项；failure 项只有在草稿判断完整语义不可表达时才给 `rejection_correct: Y` 并说明最小能力缺口，本可表达却被拒绝给 N，不确定给 ambiguous。不能仅凭交互分层统一预填某个值，也不能将执行占位等同于表示缺失；标注者独立复查。

## 5. 界面实现约束（W5 D6-D7，锁定）

**锁定实现（2026-09-02 用户决策）**：**单文件 HTML+JS，零依赖，任务 schema 由外部 JSON 驱动**。不用 Flask/web 服务（引入服务进程，委托需对方跑服务，打包变复杂）。理由：标注任务**要委托给其他标注者**（W6 扰动合理性、E1 偏好），界面必须自包含、可打包、可复用——换任务只换数据，不改界面。

**打包与委托方式**：

```
annotation_ui.html   （单文件，内嵌 CSS/JS，无 CDN，可离线打开）
        +
annotation_task.json  （任务定义：字段、选项、说明、评分说明）
        +
items.json            （任务数据：每条 {context, fields 初始值}）
        +
drafts.json           （agent 预生成草稿，可无）
        ↓ 打包成 zip 发给标注者
标注者：浏览器打开 HTML → 选文件加载 → 逐卡点击 → 导出 annotations.json
```

**标注者不需本地环境**（纯浏览器双击打开，零 Python）。**导出用「下载」按钮**（浏览器限制，标注者下载后发回/放回数据目录）。

**三种任务共用一份界面**：`annotation_task.json` 的 schema 覆盖**单选（Y/N）、三选（A/B/无法区分）、自由文本（备注/说明）**三类字段——W5 parse accuracy、W6 扰动合理性、E1 偏好各自一份 `task.json` + `items.json`，界面不改。

**界面写的字段必须与各任务的 `annotations.json` schema 一致**（W5 见 E7；W6/E1 各自定义时遵循同一约定）。

## 6. 测试与验收

- **测试**：AST 格式化器（JSON → 线性文本）单测；draft 生成器（对同一指令多次生成一致或至少格式合法）测试。
- **验收**：标注者完成 1 条记录（从加载到提交）不超过 2 分钟；标注者能**只点击**完成全部字段（无需键入除备注外内容）；输出 JSON 与 E7 schema 一致。

## 7. 任务级表示能力参考（2026-09-05 补充）

标注者需要知道本批次解析器支持的谓词、时序与逻辑组合、角色与时间约束、未支持能力，才能区分表示缺口与本可表达却未解析。每份任务在 `annotation_task.json` 的 `capabilities` 中提供统一参考（含快照版本、摘要、适用说明、分组条目及可选判断提示），所有记录使用同一份；内容由任务准备者对照 schema、解析规则与执行器整理，不从单条模型 detail 推断。

界面在「解析结果与上下文」下常驻摘要，可点击打开完整说明，failure 项同时显示合理拒绝 / 疑似漏解析 / 歧义的判断口径。参考必须区分结构可表示与可执行；特别是交互占位、受限 until，以及 turn / lanechange 的整窗或驻留限制。缺少同名谓词并不自动等于无法表达，仍需检查合法组合。

这是对原有盲评展示范围的任务级补充，单条 score、失败原因码、模型 detail 仍不显示。旧 W5 任务未附说明时展示有明确标记的内置快照，并提示先核对本批次适用性；不能把内置参考当成所有外部任务的当前能力。

## 8. 统一标注指南（2026-09-06）

以 E7 定义为准：Y＝合理拒绝，N＝本可表达却漏解析，ambiguous＝判断依据不足。`missing_capability` 仅在 failure 且 Y 时显示，保持可选；N 的可行表达或歧义依据写入备注。任务 JSON 使用 `annotation_guide.version` 固定口径版本，并通过 `principles` / `examples` 提供共同规则和边界示例；字段判据只在 `help` / `options[].description` 维护，完整指南、字段旁展开说明与 failure 提示复用同一来源。

每个口径版本首次进入时显示指南，后续随时打开，不逐条重复确认；关闭指南不会替用户提交判断。原始指令、AST、草稿均保持各自职责，指南只提供所有记录共用的规则。新提交记录写入 `annotation_guide_version`，旧版存档及导入结果保留原选择和原始导出备份，需复核后重新提交，不自动翻转 Y/N。原始人工结果文件不由界面改写。
